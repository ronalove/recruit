# recruit

CLI en Rust qui lance une équipe d'agents Claude Code dans son propre multiplexeur de terminal (sans tmux depuis la 2.0.0), à partir d'un fichier TOML. Distribué en binaires précompilés, joints aux releases GitHub de ronalove/recruit, par le tap Homebrew ronalove/tap ; Gitea (git.ronan.love) en est un miroir, qui tire GitHub : on ne pousse que sur GitHub (`origin`). Site (page d'accueil et documentation, EN et FR) : https://ronalove.github.io/recruit/, sources dans `site/`.

## Commandes

```sh
scripts/ghostty.sh                   # avant le premier cargo build d'un clone ou d'un worktree, et après une montée de version : Zig 0.16.0 et libghostty-vt dans .ghostty/, .cargo/config.toml généré
cargo build                          # binaire : target/debug/recruit (clippy ne le reconstruit pas)
cargo test                           # tests unitaires et d'intégration, sans fenêtre ni Claude
cargo fmt && cargo clippy --all-targets -- -D warnings
RECRUIT_LANG=en cargo test && RECRUIT_LANG=fr cargo test   # comme la CI
cd site && bun install && bun run build                    # le site ; un lien interne cassé fait échouer le build
scripts/screenshots.sh [--lang en|fr] [--only team|cli|anim]   # captures du site, avec de vraies sessions Claude
```

Avant de rendre un travail : `cargo fmt`, clippy sans avertissement, `cargo test` dans les deux langues. `cargo test` lance aussi les tests d'intégration du multiplexeur sans fenêtre (`tests/mux*.rs` et `tests/mux_team/` : un serveur de test, des programmes factices, un vrai client sur un terminal de test, une équipe native avec un faux claude) ; ceux qui ouvrent des fenêtres, tapent de vraies touches ou lancent de vraies sessions Claude sont ignorés et verrouillés (`KEYS_CONSENT`, `SHOTS_CONSENT`, `CLAUDE_SESSIONS` à la date du jour, et le nom du test sur la ligne de commande). La CI (`.github/workflows/ci.yml`, GitHub Actions) les lance sous Linux et macOS à chaque push sur `main`, à chaque pull request vers `main` et à la main (`gh workflow run ci.yml --ref <branche>`), et construit les binaires musl ; `pages.yml` publie le site quand `site/` change. Plus de Woodpecker pour recruit (désactivé le 2026-10-08).

## Publier une version

`scripts/release.sh X.Y.Z [notes.md]`, sur un Mac, depuis `main` propre et à jour : version dans Cargo.toml, vérifications, binaires macOS (chaîne d'Apple) et Linux musl statiques (cargo-zigbuild : `brew install zig cargo-zigbuild`), commit et étiquette `vX.Y.Z`, release GitHub par `gh` (connecté au compte ronalove) avec les archives et `SHA256SUMS`, puis formule régénérée et poussée dans le tap ronalove/homebrew-tap (son clone `../homebrew-tap`, ou `TAP_DIR`). `--dry-run` construit seulement, dans `target/dist/`. Les notes de version s'écrivent dans `target/notes/X.Y.Z.md` (jamais commitées, jamais à côté du dépôt), et partent après la publication. La formule ne s'édite pas à la main : son modèle est dans le script. Avant toute publication, la formule et celles du tap passent la vérification de `brew tap` (fonction `check_formulae`, par `brew ruby`) : chaque formule doit se charger sur tous les systèmes et processeurs connus de Homebrew, sinon `brew tap ronalove/tap` refuse tout le tap et efface son clone (le 2026-10-09, `ccfaststatus.rb`, qui n'avait d'URL que dans `on_macos`). `brew install` et `brew update` ne la font pas : un tap cassé ne se voit qu'à un `brew tap` neuf.

## Organisation

- À la racine de `src/`, l'entrée et ce que tout le monde partage : `main.rs` ; `cli.rs` : ligne de commande (clap), aide traduite dans `localize` ; `app.rs` : ce que fait chaque commande, et les trois scénarios d'un `recruit` sans argument ; `i18n.rs` : langue (FR, EN), `t!("français", "english", args…)`, `t!(in lang; …)` pour la langue d'une équipe, `joined` (« a, b et c ») ; `sys.rs` : ce que tout le monde demande au système (dossiers de l'utilisateur, `tilde`, `cache_dir`, `write_atomic`, `now`, `exe`, `fnv64`). Le reste en domaines, chacun en `x.rs` + `x/`.
- `config.rs` + `config/` : fichiers d'équipe (`.recruit/settings.toml` fusionné avec `settings.local.toml`, `~/.config/recruit/<équipe>.toml` ; `local_files`), validation, `auto_compact` (`AutoCompact`, `Team::auto_compact_at`, de 1 à 100), grille par défaut (`COLUMNS`, `ROWS`), langue d'une équipe (`Team::language`), écriture qui garde les commentaires ; `config/check.rs` : ce que recruit refuse dans les fichiers (noms réservés `RESERVED`, tenus à jour par un test contre les sous-commandes de clap, règles des noms, titres d'onglets de recruit, rôle manquant, trop d'interlocuteurs) ; `config/edit.rs` : les modifications du menu (`config::edit`, une écriture groupée et validée), dans le fichier qui donne la valeur, et les réglages d'équipe du menu (`team_layers`, `Edit::Grid`, `Edit::Layout`, `Edit::AutoCompact`).
- `create.rs` + `create/` : création d'une équipe : l'assistant (`create.rs`), `recruit new` sans question (`new.rs`), l'équipe ou le membre composés par `claude -p --json-schema` (`compose.rs`), les équipes intégrées (`templates.rs`, avec `templates/` à la racine du dépôt : `catalog.toml` donne les rôles de chaque type et de chaque taille, `fr.toml` et `en.toml` leurs textes).
- `team.rs` + `team/` : une équipe au travail. `launch.rs` : son lancement (son plan, son serveur, la reprise après un plantage ; `Panes` construit les panneaux des membres et des tableaux, au lancement comme à chaud) ; `live.rs` : une équipe lancée qui suit ses fichiers après une modification (ajout, retrait, renommage, relances, panneaux déplacés entre onglets sans être arrêtés), et l'ouverture du menu ; `state.rs` : l'équipe telle que lancée, dans `~/.cache/recruit/teams/<session>/team.json`, que lisent les panneaux ; `layout.rs` : répartition en onglets ; `prompt.rs` : prompt système de chaque membre ; `member.rs` : ce qui tourne dans le panneau d'un membre (`recruit _member [--resume] <dossier> <membre>`) : son Claude, relancé sur la même session quand il s'arrête de lui-même ; la session courante est lue dans le fichier que Claude Code tient pour son processus (`<profil>/sessions/<pid>.json`, `sessionId`), à défaut dans `states.json` (même pid exigé), puis par `claude agents`, et notée dans `sessions/<membre>` du dossier de l'équipe ; un départ sur une conversation (`-r <id>` après `-n`) la note tout de suite, un départ à neuf efface la note.
- `claude.rs` + `claude/` : Claude Code. `claude.rs` : exécutable (le premier du `PATH` qui s'exécute), profil, `claude agents --json`, approbation du dossier, version (`claude_version`, `MIN_CLAUDE`) ; `session.rs` : fichiers de session (le pid vérifié), transcriptions, reprise des conversations, référence d'une session (`session_ref`) ; `args.rs` : ligne de commande d'un membre (`Launch`), ligne d'état de l'utilisateur. `claude/bridge.rs` + `bridge/` et `mod/` : le mod de recruit (plugin de hooks en TypeScript, embarqué, écrit dans `~/.cache/recruit/mod/<version>/`, passé par `--plugin-dir` si Claude Code ≥ 2.1.287). Le mod est une passerelle sans logique : il appelle `recruit _mod start|tick|submit|command <dossier> <membre>`, JSON en entrée et en sortie, et le pont fait le travail (`report.rs` : rapports pour le tableau de bord ; `models.rs` : la table des modèles et des efforts (`MODELS`, `EFFORTS`) ; `tick.rs` ; `requests.rs` : compaction et « Reprendre » demandés depuis le tableau de bord, le menu ou le serveur (`request_auto_compaction`, avec des instructions) ; `prompt.rs` : note de l'équipe à jour, dans sa langue ; `command.rs` : `/equipe`, `/recruit` ; `helpers.rs` : sous-agents et teammates ; `doing.rs` : ce que fait chaque membre ; et la dernière compaction faite, automatique, à la main ou `/compact` tapé (`Report.compacted`, `last_compacted` en JSON)).
- `ui.rs` + `ui/` : ce qui se dessine et se demande sur un terminal. `canvas.rs` + `canvas/` : un écran entier dessiné case par case (`Canvas`), mesuré en colonnes (`canvas/text.rs` : `columns`, `text_columns`, `fit`, `wrap` et `wrap_chars` (le retour à la ligne aux mots de tout recruit), `is_direction_mark`), envoyé par différence avec l'image d'avant (`canvas/painter.rs`, `Painter`, en mise à jour synchronisée pour le tableau de bord et le menu) ; `terminal.rs` : le terminal rendu tel qu'il était à chaque sortie, panique comprise (`Session`, `PanicGuard`) ; `look.rs` + `look/` : ce que partagent le tableau de bord, le menu et le multiplexeur (états et leurs icônes, Nerd Font ou Unicode (`Glyphs::of`, d'après les terminaux des clients), indicateur animé, durées ; `look/effort.rs` : signes et noms de l'effort, initiale du modèle, `shown` ; `look/palette.rs` : les deux palettes de recruit (`Palette`, `DARK`, `LIGHT`, `palette()`, `set_light`), choisies par le fond du terminal du client, couleurs des membres ; `look/error.rs` : libellés courts d'une erreur d'API) ; `ask.rs` : invites (texte et oui/non par inquire) ; `list.rs` : listes de choix dessinées par recruit (crossterm), sans curseur ; `print.rs` : une équipe affichée en texte ; `Rect`, `Rgb`.
- `board.rs` + `board/` : panneaux d'une équipe lancée (`recruit _panel dashboard|journal <dossier>`, sous-commande cachée, des programmes dans leurs panneaux) ; le tableau de bord (`dashboard.rs`) est le seul à lancer `claude agents` (toutes les 5 s, chaque seconde tant qu'un membre n'a pas d'état OSC), prend les états au serveur (`Mux::panes`, OSC 7501), se redessine en entier sur SIGWINCH (`keyboard.rs`) et se dessine par `Canvas` et `Painter` ; il écrit aussi, chaque seconde, pour le menu, le journal, les membres et le serveur, `states.json` (`states.rs` : l'état de chaque membre et depuis quand, `at` en secondes, une commande en cours, les adresses exactes des doublons, la session et le processus de chacun ; effacé au lancement d'une équipe) et `zones.json` (`zones.rs` : où cliquer) ; `board::looks` donne au serveur ce qu'il écrit dans les en-têtes ; le dessin d'une carte (`card.rs`) est partagé avec les cartes du focus (`CardData`, `card_lines`, `card_rows`), et `states.json` porte aussi `cards` (ce que fait chaque membre et sa courbe, `Activity`) ; la disposition des cartes dans `arrange.rs` ; sous les membres, les sections « ♙ teammates » puis « ⧗ sous-agents » (`agents.rs`) ; le journal (`journal.rs`) porte aussi les compactions.
- `menu.rs` + `menu/` : le menu principal (`recruit _menu <dossier> [--client <nom>] [--nerd] [--light] [--member m [--field f] [--list]]`, dans un calque que le serveur ouvre au centre, le reste atténué) ; `menu/quick.rs` : la liste du modèle ou de l'effort sous un en-tête (`--list`), dans un panneau flottant à sa taille, qu'elle demande au serveur par `CSI 8 ; lignes ; colonnes t` ; `menu/sheet.rs` + `sheet/` : son état et ce que fait chaque touche ou clic, sans terminal ni fichiers (ce qui touche l'équipe revient en `Effect`, que `menu/effects.rs` exécute) ; `menu/draw.rs` + `draw/` : le dessin et les zones de clic. Des fichiers d'équipe illisibles l'ouvrent en lecture seule (membres tels que lancés, détacher, arrêter). `recruit _edit` (caché) applique des modifications sans menu, pour les tests.
- `mux.rs` + `mux/` : le multiplexeur (spec et journal : `specs/multiplexeur.md`). Un serveur par équipe (`recruit _server`, détaché, verrou et `server.json` dans le dossier d'état, socket dans `${RECRUIT_TMPDIR:-/tmp}/recruit-<uid>/` ; `socket.rs`, `crashed`, `recovered`) ; `handle.rs` : `Mux`, la poignée sur le serveur d'une équipe, une méthode par requête, que le reste de recruit utilise (`Mux::of(session)`, `Mux::at(dossier)`) ; `plan.rs` : ce qu'un lancement lui demande (`Plan`, `Pane`) ; un client mince (`recruit attach`, `client.rs`), leur protocole (`proto.rs`, JSON tramé, `PROTO`), `_ctl` pour les tests (capture, send, key, panes, stats). `pty.rs` + `pty/child.rs` : le PTY de chaque panneau, et ce que fait l'enfant entre `fork` et `exec` ; `engine.rs` + `engine/` : le moteur VT derrière les traits `Surface` (ce que lisent l'écran et la sélection) et `Engine` (libghostty-vt, `engine/ghostty.rs` et `ghostty/frame.rs`, construit par `scripts/ghostty.sh` ; un renifleur, `sniff.rs`, pour ce qu'il laisse passer : OSC 7501, notifications OSC 9, 777, 99, progression OSC 9;4, RIS, fin de mise à jour synchronisée (2026), mode 2031 demandé, mode 2027 coupé par un programme, XTWINOPS 8) ; `screen.rs` : composition des panneaux, des calques et de la notification (`Scene`), gardée d'une image à l'autre ; `chrome.rs` + `chrome/` : cadres et en-têtes (`frame.rs`), barre (`bar.rs`), notification, choix (direction « Cadres ») ; `input.rs` + `input/` (`terminal.rs` : le terminal du client ; `probe.rs` : sa sonde ; `parse.rs`, `encode.rs`) et `keys.rs` : lecture du terminal du client et raccourcis ; `select.rs` : sélection et copie ; `layout.rs` : géométrie d'un onglet en grille ou en focus (`rects`, `focus_room`, `focus_rects`, `focus_cards_rows`) ; `server.rs` + `server/` : la boucle du serveur et ses sous-modules (`lifecycle`, `clients`, `tabs`, `panes`, `requests`, `events`, `mouse`, `menu`, `notice`, `status`, `frame`, `focus_layout`, `choice`, `pane`), la compaction automatique (`compaction.rs` : `compaction_due`, `renewal`, `settle_compactions` ; `RECRUIT_AUTO_COMPACT_IDLE`, caché, en secondes, pour les tests) ; `focus.rs` : les places d'un onglet en focus (gauche, droite, cartes), sans horloge ni terminal ; `cards.rs` : les cartes « autres » du focus, dessinées par `board::card_lines` dans un `Panel` (une `Surface`).
- `site/` : Astro Starlight, construit par bun. La documentation dans `src/content/docs/` (anglais) et `src/content/docs/fr/` (mêmes noms de fichiers), la page d'accueil à part, sans l'habillage de Starlight, les captures dans `src/assets/screenshots/`.
- `scripts/screenshots.sh` + `scripts/shots-ctl.sh` + `scripts/demo/` : les captures et l'animation du site et des README, faites avec une équipe de démo (« shorty »), de vraies sessions Claude, vhs et ffmpeg ; `RECRUIT_NO_USAGE=1` (caché) y masque la ligne d'usage du tableau de bord.
- `scripts/ghostty.sh` : Zig 0.16.0 et libghostty-vt (sources de Ghostty à un commit fixé, vérifiées par leur somme), dans `.ghostty/`, et `.cargo/config.toml` qui les relie ; la CI le lance avant Cargo.
- `tests/` : les tests d'intégration, sans fenêtre (`common/` : serveur de test, faux programmes, terminal de test, équipe avec un faux claude ; `mux_team/` en modules par sujet), et ceux qui ouvrent des fenêtres, tapent de vraies touches ou lancent de vraies sessions Claude, ignorés et verrouillés.
- `specs/` : la spec du multiplexeur (`multiplexeur.md`, journal des décisions au §11), la grille de compatibilité avec Claude Code (`multiplexeur-compat.md`), le plan et le journal de la refactorisation (`refacto.md`) ; les documents de la construction (suivi, prototype, protocole du serveur, inventaires de la refactorisation) dans `specs/archive/`.

## Décisions (validées par l'utilisateur, octobre 2026)

- 2.0.0 (décision du 2026-10-10) : recruit a son propre multiplexeur ; tmux n'est plus utilisé ni requis. Plus rien de la 1.x depuis la refactorisation (décision du 2026-10-11) : une section `[tmux]` est une clé inconnue, refusée comme les autres, et une équipe encore sous le tmux de la 1.x n'est plus reconnue. Claude Code seulement ; FR et EN ; pas de pilotage de Ghostty ni d'iTerm2.
- Une équipe globale n'a pas de dossier : elle travaille dans le dossier où on la lance. Locale et globale ne diffèrent que par l'endroit d'où on peut la lancer.
- `recruit` sans argument : équipe locale → lancée tout de suite ; sinon équipes globales → proposées, jamais lancées sans demander ; sinon → création interactive. `recruit <nom>` : la locale prime sur la globale ; inconnue → création.
- Mode guidé : modèles intégrés (type × taille), plus l'option « Claude compose l'équipe ». Claude compose par métier, comme les rôles intégrés (2026-10-07) : noms de métier (un rôle intégré, sinon métier-spécialité comme `dev-rust`), jamais deux zones collées, accents compris en français.
- Interlocuteurs et agents de travail (décision du 2026-10-06) : `contact = true` marque les membres à qui parle l'utilisateur (à défaut, le premier membre).
  - Disposition : un premier onglet « Interlocuteurs », puis les agents de travail par `tab`, ou dans « Agents ». Chaque groupe fait au plus `columns` × `rows` (3 × 2 = 6 par défaut, réglables au menu, « Grille »), réparti à parts égales en « Agents (1) », « Agents (2) »…, y compris pour une petite équipe.
  - Tous les agents gardent un panneau visible, jamais `--bg`.
  - Le prompt dit à un agent de travail de passer par les interlocuteurs plutôt que d'attendre dans son terminal.
- Tableau de bord (décision du 2026-10-07) : deux interlocuteurs au plus, empilés à gauche du premier onglet ; à droite, le tableau de bord au-dessus du journal, lancés par recruit lui-même et nourris de `claude agents --json` et des transcriptions. `Alt+j` fait passer le journal de complet à réduit (ses trois derniers messages), puis masqué, puis complet (2026-10-07) ; il est réduit au lancement. `dashboard = false` s'en passe (interlocuteurs côte à côte).
- Panneaux, direction B choisie sur maquettes (2026-10-07) : une carte par membre (nom, temps dans l'état, courbe d'activité sur 30 min, contexte), cadre à la couleur de l'état (jaune au travail, vert au repos, rouge en attente), sans modèle, effort ni dernier outil. Disposition : voir plus bas. Journal : deux lignes par message. Maquettes : https://claude.ai/artifact/CztErLpVy96TGm4doc9kZS
  - Retouches (2026-10-07) : indicateur animé à gauche du nom au travail, icône de l'état sinon. En haut : l'heure, le nombre de membres par état en icônes et les raccourcis (remplacé à l'étape 3 du multiplexeur, voir plus bas) ; plus de légende, et plus le nom de l'équipe, déjà dans la barre. En bas : l'usage 5 h / 7 j sur une ligne. Icônes Nerd Font quand le terminal les embarque (Ghostty, kitty, WezTerm), Unicode d'une colonne sinon ; pas de dépendance à une police.
  - Cartes sur deux lignes, variante « Trait » (2026-10-07, maquette https://claude.ai/artifact/QsLCTZPnNqgkg1ij8T3VMf ; remplace le cadre et les couleurs ci-dessus) : à gauche, un trait « capsule » à la couleur de l'état, sur toutes les lignes de la carte (╻ en haut, ┃ au milieu, ╹ en bas : il commence et finit au milieu de la première et de la dernière ligne, et deux cartes ne se touchent pas), une ligne vide entre les cartes, courbe inchangée. L'état se lit par l'intensité : au travail jaune vif et nom en gras, en attente rouge vif, au repos gris et nom atténué. Dans le titre, à gauche du temps, le modèle (Haiku, Sonnet, Opus, Fable) et l'effort aux couleurs de Claude Code, selon la place : « Opus █ xhigh » (signe de niveau et mot, signes et noms remplacés le 2026-10-11, voir « Signes de l'effort et du modèle » ; low jaune, medium vert, high et xhigh violet, max arc-en-ciel), sinon « Opus █ », sinon « Opus », sinon rien, la même forme pour toutes les cartes de même largeur ; le modèle, l'effort et le temps alignés en colonnes d'une carte à l'autre de même largeur, le temps écrit court (12s, 22m, 1h05) ; le modèle toujours atténué ; l'effort toujours vif. Une ligne « ce qu'il fait », selon la forme de la carte, sur deux lignes au plus quand le texte dépasse et qu'il y a la place (coupé aux mots ; « … » seulement faute de place) : un résumé de la demande en cours par Haiku (`$.model.complete` dans le mod, préparé par `bridge.rs`), une fois par nouvelle tâche ; les modèles actuels n'ont plus de liste de tâches ; au repos, la dernière tâche, atténuée, sous sa forme finie (« ✓ Version 0.6.2 publiée »), que Haiku donne dans le même appel. Le contexte passe en orange dès 80 % du seuil de compactage automatique du modèle, en rouge à l'avertissement de Claude Code (20 000 jetons avant) ; un clic sur celui d'un membre au repos propose de compacter, après confirmation.
  - Clic (2026-10-07) : un clic sur la carte d'un membre, ou sur l'expéditeur ou le destinataire d'un message du journal, mène à son panneau.
  - Disposition (2026-10-07) : les interlocuteurs, puis les agents en attente, ceux au travail, puis ceux au repos du plus récent au plus ancien. Chaque carte a sa forme : pleine largeur avec ce qu'il fait sur deux lignes ou une, côte à côte avec une ligne ou aucune, ou, pour un agent au repos, son nom dans la liste. Dans cet ordre, chaque carte prend la plus riche qui laisse la place à toutes les suivantes dans leur forme la plus sobre. Les actifs restent en pleine largeur sans texte coupé tant que possible : la liste des noms au repos se réduit à une ligne (« … et N autres ») avant qu'un actif perde du texte. Une carte sans tâche commence côte à côte et ne s'élargit qu'avec la place qui reste. En dernier recours, « … et N de plus ». La disposition ne change qu'avec les cartes, leurs états ou le panneau.
- Barres de Claude Code (décision du 2026-10-07) : sauf l'interlocuteur principal (le premier interlocuteur), les membres n'ont ni la ligne d'état de l'utilisateur (`--settings` au lancement, pour la session seulement, et seulement si ses réglages en définissent une ; en plein écran, sa ligne reste, vide) ni l'aide du bas (le mod masque `PromptHint` et `SessionMode`). La saisie et la ligne du mode de permission restent : en 2.1.292, rien ne peut les masquer, ni les lier au focus.
- Stabilité et sortie (décision du 2026-10-07) : un membre arrêté (`/exit`, plantage) est relancé après 2 s sur sa session (Ctrl-C : un shell à la place ; pas de relance après deux départs ratés ni à l'arrêt de l'équipe). Revenir sur une équipe qui tourne relance les membres arrêtés, rouvre le tableau de bord, propose de reconstruire si des panneaux manquent. `Alt+q` et le bouton « quitter » de la barre ouvrent un menu : détacher ou arrêter l'équipe.
- Plantage du serveur (décision du 2026-10-09) : les membres reprennent leur conversation sans demander, en le disant ; une seconde reprise dans les dix minutes demande d'abord. Un plantage se reconnaît à la marque `crashed` (le `server.json` d'un serveur mort) et à un verrou libre ; un `recruit stop` qui doit tuer un serveur bloqué est un arrêt voulu.
- Mod passerelle (décision du 2026-10-07) : toute la logique reste en Rust. Il ajoute au tableau de bord le modèle, l'effort, le contexte et l'usage 5 h / 7 j, sert `/equipe` (`/team`) et `/recruit` (voir « Menu principal »), et donne à chaque membre la composition à jour de l'équipe.
- Menu principal (décision du 2026-10-07) : `/recruit` (même nom en FR et EN) remplace `/regler`. Il s'ouvre en calque au centre, le reste atténué. `Alt+r` l'ouvre aussi, sur la fiche du membre actif, ainsi qu'un bouton « menu » dans la barre, à gauche de « quitter » ; un clic sur le nom, le modèle ou l'effort d'un en-tête l'ouvre sur ce champ ; `Alt+q` ouvre le choix Détacher, Quitter, Annuler.
  - Entrées : pour chaque agent, modèle, effort, nom, rôle et instructions, interlocuteur, onglet, mode de permission, relancer (en reprenant sa conversation ou à neuf), retirer ; nouvel agent (rôle intégré, composé par Claude, ou saisi) ; pour l'équipe, tableau de bord oui ou non, tout recharger à zéro (contextes vidés pour tous), détacher, arrêter.
  - Les modifications sont permanentes et prennent effet tout de suite sur l'équipe lancée. Elles s'écrivent dans le fichier qui donne aujourd'hui la valeur (`settings.local.toml` s'il a la clé, sinon `settings.toml` s'il l'a, sinon le fichier qui définit le membre ou l'équipe, `settings.toml` d'abord), jamais dans `~/.claude/settings.json` ni ailleurs. ## Pièges

- Les panneaux des membres lancent `/bin/sh -c 'trap : INT; <claude …>; exec "$SHELL" -l'` : le shell qui reste après Claude doit être celui de l'utilisateur, et le script doit être POSIX (le shell par défaut peut être fish). Le `trap : INT` garde le script en vie quand Ctrl-C arrive pendant la pause avant une relance (dash et ash s'arrêtent sinon, sans laisser de shell) ; il n'est pas hérité par Claude ni par le shell final.
- Un `--dry-run` ne finit pas sur un shell de connexion : son message d'accueil recouvrirait le texte du panneau.
- Le mod : `/model` et `/effort` lancés par `$.command.run` enregistrent le choix comme défaut de l'utilisateur dans `~/.claude/settings.json`. Le modèle et l'effort changés depuis le menu passent donc par `turn.step` (`next({ ...e, model, effort })`), là seulement où `MemberInfo.model`/`effort` diffèrent de `--model`/`--effort` de `MemberInfo.argv`. `turn.step` veut un identifiant complet (`sonnet` y échoue) : `bridge.rs` traduit les alias (table `ALIASES`, à tenir à jour). Le retour au défaut de Claude Code, ou un modèle sans identifiant connu (`opus[1m]`), ne passe pas par la requête : `bridge::applies_live` le dit, et le membre est relancé avec reprise. Le mode de permission ne change pas à chaud (`setMode` n'existe que dans la réponse à une demande de permission) : relance avec reprise. En testant avec de vraies sessions, vérifier que `<profil>/settings.json` (`~/.claude`, ou `$CLAUDE_CONFIG_DIR`) ne change pas.
- Le prompt de `--append-system-prompt-file` n'est ni une section de `prompt.section` ni de `prompt.compose` (2.1.293) : il s'ajoute après, et une conversation reprise par `-r` le garde tel qu'au départ. Le prompt à jour passe donc par une note jointe au message entrant (`prompt.submit`, `context`), que l'utilisateur ne voit pas : `_mod submit` ne la donne que si le prompt a changé depuis ce que la conversation a reçu (`prompted/<session>.json` du dossier d'état), et de nouveau après une compaction ; en échec, ou au-delà de 3 s, le message passe sans note. Le `--append-system-prompt-file` de `MemberInfo.argv` nomme le prompt d'une conversation neuve, même pour un membre repris : une conversation reprise se reconnaît à son fichier, déjà là au démarrage (une neuve ne l'a qu'à son premier message). Les prompts sont écrits un fichier par contenu, jamais réécrits en place.
- Le mod se vérifie avec `claude plugin validate mod` (fait par `release.sh`), ses types avec `bunx -p typescript tsc -p mod` : Claude Code écrit ceux de sa version dans `mod/.claude-plugin/types/` (ignorés par git) dès qu'il charge `--plugin-dir mod` ; le fichier installé avec le marketplace peut dater d'une version antérieure. Le validateur exige `$` passé seulement à des fonctions de premier niveau, et `$.env.get` avec un nom littéral.
- Les commandes que le mod enregistre (`$.command.register`) ne prennent pas l'espace de noms du plugin : `/recruit` marche bien que le plugin s'appelle recruit ; Claude Code préfixe seulement leur sortie par « recruit: ».
- Reprendre la session d'un membre : pas la plus récente qui porte son nom (une session qui n'a rien échangé n'a pas encore de titre, et une plus ancienne serait reprise), mais celle que `member.rs` a relevée pendant qu'elle tournait.
- Le mod remplace `PromptHint` par trois blancs en `marginLeft: -3` (`noHint`), dessinés sur le « · » que Claude Code laisse après le libellé du mode. C'est fragile : si Claude Code change ce séparateur, ou met l'aide avant le mode, le « · » revient sans bruit. Quand le libellé passe à la ligne (panneau très étroit : 26 colonnes en mode bypass), le « · » reste, comme sans `noHint` (vérifié en 2.1.293).
- En plein écran, Claude Code garde une ligne pour toute `statusLine`, même une qui n'affiche rien, et `--settings` ne peut pas l'enlever (2.1.293). QUIET ne fait donc que remplacer celle des réglages, et ne se passe que s'il y en a une (`claude::status_line`) : sinon, il ajouterait sa propre ligne.
- Les réglages que lit Claude Code (2.1.293) : `<profil>/settings.json` ; `<cwd>/.claude/settings.json`, jamais à la racine git ; `<racine git>/.claude/settings.local.json`, plus l'ancien `<cwd>/.claude/settings.local.json`. La racine d'un worktree est son dépôt principal (Claude Code suit `.git`, `gitdir` et `commondir`), sauf pour un dépôt nu. Les réglages gérés priment sur `--settings`.
- Les listes de choix (`ui/list.rs`) se redessinent en place : elles remontent d'autant de lignes qu'elles en occupaient (largeurs en colonnes, `unicode-width`). Quand le terminal rétrécit, un terminal comme tmux replie les lignes trop longues et garde ce repli sur les lignes réécrites ensuite ; élargi, il les recolle, la liste tient moins de lignes que prévu et le redessin efface ce qui est au-dessus. Chaque redessin efface donc sa première ligne entière (`Clear(CurrentLine)`), l'écrit, puis efface jusqu'en bas (`Clear(FromCursorDown)`) : effacé jusqu'en bas depuis le coin en haut à gauche, l'écran entier passerait dans l'historique de tmux (`scroll-on-clear`) à chaque touche (vérifié en 3.7c). La place sous la liste vient de `cursor::position()`, qui interroge le terminal par stdout : seulement si stdout est le terminal.
- Le menu ne fait rien de lent avant sa première image : le serveur le lance dans un panneau flottant à la taille du calque, avec `--client` et `--nerd` (ce qu'il sait du terminal du client) ; les états viennent de `states.json` s'il date de moins de 3 s (`at`), sinon de `claude agents --json` toutes les 2 s, dans un fil à part ; un état qui ne se voit pas compte comme peut-être au travail.
- `canvas` : `put` garde un accent (un caractère sans largeur) dans la case du caractère d'avant, et écarte les autres caractères sans largeur (ZWJ, sélecteurs de variante, caractères de format, marques de direction) ainsi que les contrôles ; chaque caractère est mesuré seul, donc une séquence d'emoji écrite par `put` s'affiche en morceaux. Les cases des panneaux viennent entières de leur moteur (`put_cell`, qui n'écarte que les contrôles, les marques de direction, un sélecteur de variante 16 sur une case d'une colonne et un ZWJ en fin de case). Le client garde le mode 2027 d'un terminal qui l'a allumé (Ghostty) et l'allume chez un terminal qui le connaît éteint, puis le remet tel qu'il était à toute sortie (`GRAPHEMES_ON`) : les cases s'y écrivent entières. Le moteur garde ses grappes quoi que demande le programme (`set_default_mode`, qui survit à un RIS, et `Sniffed::GraphemesOff` sur un `?2027l`) : le vrai terminal, lui, ne change pas de mode. Un terminal qui ne mesure pas les graphèmes (mode 2027 absent, `Features.graphemes`) reçoit une case de plusieurs caractères réduite à ce qui tient dans ses colonnes (👍🏽 devient 👍), pour que la ligne reste alignée. Après une case de plusieurs caractères, le `Painter` replace le curseur avant la case suivante, car le terminal peut l'avoir mesurée autrement.
- Les fichiers que lisent d'autres processus (`states.json`, `zones.json`, rapports et notes du mod) s'écrivent par `sys::write_atomic`, la seule écriture atomique : un `.<nom>.<pid>.tmp` à côté, puis renommé. Une lecture de dossier doit écarter ces fichiers (`prompted/` ne garde que les `.json`).
- La langue est fixée une fois par processus (un `OnceLock`), donc pour tous les tests à la fois : un test qui compare un texte le construit par `t!` (ou `look::ALT` pour ⌥/Alt+), jamais en dur. La CI tourne sans locale (anglais) : `RECRUIT_LANG=en cargo test` le reproduit.
- Sous Linux, l'heure d'un fichier vient d'une horloge grossière (un tick) et peut précéder un `SystemTime::now()` pris juste avant l'écriture : ne jamais comparer l'heure d'un fichier à l'heure courante pour savoir s'il est neuf ; écrire un jeton et comparer le contenu.
- Captures : Claude Code affiche le forfait du compte (« Claude Max ») dans son accueil, sans réglage pour le masquer (2.1.294) ; `scripts/screenshots.sh` relit chaque panneau avant de capturer et recommence tant qu'un forfait, `/Users/` ou `$HOME` s'y voit. `vhs -q` (0.12.1) quitte avant d'écrire une capture qui termine la tape : une pause en fin de tape.
- Le multiplexeur se construit avec libghostty-vt : `scripts/ghostty.sh` avant le premier `cargo build` d'un clone ou d'un worktree, et après une montée de version de Ghostty ou de Zig ; sans lui, la liaison échoue. Zig 0.16.0 exactement (0.15 ne lie pas avec le SDK de macOS 26.4 et plus) ; sans réseau, `GHOSTTY_SOURCE_DIR` et `GHOSTTY_ZIG_SYSTEM_DIR`, que lit le `build.rs` de la crate quand `scripts/ghostty.sh` n'a pas tourné.
- Un panneau ne doit hériter d'aucun descripteur du serveur (le lanceur, un runner de CI en laisse sans CLOEXEC) : l'enfant ferme tout au-dessus de 2 avant `exec` (`close_range` sous Linux 5.9 et plus, sinon une boucle bornée), rien d'autre entre `fork` et `exec`.
- Mode 2026 (mises à jour synchronisées) : le délai de garde est d'une seconde, comme Ghostty (`SYNC_TIMEOUT`) ; plus court, une image s'affiche à moitié quand le PTY est lu lentement (petit tampon sous macOS, machine chargée). Une même lecture peut finir une mise à jour et en commencer une autre : chaque fin remet l'échéance à zéro (`Sniffed::SyncEnd`).
- Le socket d'une équipe vit dans `${RECRUIT_TMPDIR:-/tmp}/recruit-<uid>/` : sous macOS, `sun_path` tient 104 octets, et un dossier de test sous `/var/folders/…` les dépasse. Les tests donnent un `RECRUIT_TMPDIR` court, à eux, en plus de `XDG_CONFIG_HOME` et `XDG_CACHE_HOME`.
- Après la première version publiée avec le multiplexeur, toute variante ajoutée à une requête ou une réponse du protocole fait monter `PROTO` : un pair plus ancien ne la lirait pas. Un champ optionnel (`#[serde(default, skip_serializing_if = …)]`), qu'un pair plus ancien ignore, ne la fait pas monter ; il entre au test de référence du protocole (`the_protocol_is_as_numbered`).
- Ne jamais découper un texte avec une position trouvée dans une autre chaîne, même sa version en minuscules : `to_lowercase` change la longueur en octets de certains caractères (« İ », « Ⱥ ») ; découper la chaîne où l'on a cherché. Un texte d'erreur écrit par un panneau (OSC 7501 `msg`) a fait paniquer le serveur ainsi (trouvé en relecture, 2026-10-10).
- Le mod : `$.prompt.submit` d'un plugin passe par la file des commandes (2.1.296), jamais par la saisie, et attend que la session soit libre ; un brouillon reste intact, et `$.prompt.read()` le donne. « Reprendre » vérifie qu'aucun tour ne tourne (`turn.start`/`turn.complete` sans `agentId`) avant et après la lecture, puis envoie « continue » avec `asUser`.
- `claude agents --json` coûte ~0,2 s de CPU et ~160 Mo par appel (2.1.296) : appelé chaque seconde par le tableau de bord, le journal et chaque membre, une équipe de 12 en faisait ~2 par seconde, 0,4 cœur en continu (2.0.0). Seul le tableau de bord l'appelle ; les autres lisent `states.json` ou le fichier de session de Claude. Les garde-fous de `tests/mux_team/` comptent les appels du faux et les octets du tableau de bord.
- OSC 7501 (Claude Code 2.1.296) : en plus de son propre état (jamais d'`id`), Claude annonce chaque sous-agent (`state=working:app=claude-code:id=<id>:title=…`) et l'efface à sa fin (`state=clear:id=<id>`) ; ces entrées ne touchent pas l'état du panneau. Son `state=clear` sans `app` (sortie, démontage de son composant de statut) rend le panneau sans état sans désarmer le moteur ; seul `state=clear:app=recruit`, écrit par `member.rs` quand son Claude s'arrête, le désarme, et Claude ne refait jamais `OSC 7501 ; ?`. `state=error` (tour raté sur une erreur d'API) se lit comme un tour fini. Un panneau sans état prend celui du tableau de bord.
- Tester une équipe lancée : `recruit _ctl` (caché) parle au serveur comme le ferait un client (capture d'un panneau, texte ou touches envoyés, liste des panneaux, mesures), sans terminal ni fenêtre. Les tests d'équipe lancent un faux claude (`tests/common/team.rs`) avec un profil temporaire (`CLAUDE_CONFIG_DIR`) : il n'a d'état qu'après avoir écrit `OSC 7501 ; ?`, et il écrit une ligne `custom-title`, sans laquelle aucune session n'est reprise. Ne jamais toucher au serveur ni aux équipes de l'utilisateur.
- Vraies frappes (System Events), captures de fenêtres et vraies sessions Claude : seulement avec le go de l'utilisateur pour la journée (`KEYS_CONSENT`, `SHOTS_CONSENT`, `CLAUDE_SESSIONS` à la date du jour, et le test nommé). Les frappes vont à la fenêtre qui a le focus : vérifier son titre et une touche témoin avant de taper. Avec un vrai Claude Code : taper le texte, attendre 0,7 s, puis Entrée à part (sinon c'est un collage) ; la question de confiance du dossier veut Bas puis Entrée. Chaque dossier de test laisse un projet sous `~/.claude/projects` et une approbation dans `~/.claude.json`, à retirer seulement quand aucun Claude ne tourne (il réécrit ce fichier sans cesse).
- Sous macOS, écraser par `cp` un exécutable qu'un processus vivant fait tourner fait tuer (SIGKILL, code 137) chaque nouveau lancement de ce fichier (signature en cache) : copier sous un autre nom, puis `mv`. Une équipe lancée depuis `target/debug/recruit` s'arrête donc mal après un `cargo build` qui le remplace en place ; pour une équipe qui dure, une copie à part.
- Sous Linux (ext4), un fichier retiré puis recréé peut reprendre le même numéro d'inode : ni l'inode ni l'heure ne disent qu'un fichier est neuf, un jeton dans son contenu si.
- Tester sous Linux sur ce Mac (OrbStack) : des images arm64 natives (`--platform linux/arm64`, `alpine:3.22`, `ubuntu:24.04`) et `--init` ; en amd64, Rosetta garde des descripteurs ouverts et fait échouer à tort les tests de descripteurs.
- Le rapport d'un membre (`claude::bridge::Report`) se lit directement de l'entrée du tick du mod : un champ de `Report` ne porte jamais le nom d'une clé de cette entrée (`session`, `model`, `own`, `context`, `rateLimits`, `threshold`, `compacted`, `agents`, `summary`, `compaction`, `resumption`, `typed`) avec un autre sens ou un autre type : chaque tick échouerait, et le rapport serait vidé (`Report.compacted` l'a fait, trouvé en vraies sessions le 2026-10-11). Un champ propre au pont prend un nom à lui (`rename`). Une entrée illisible garde le rapport d'avant (son heure comprise) et le dit une fois dans `server.log` (`input_error`).
- Compaction et OSC 7501 (Claude Code 2.1.296, relevés réels du 2026-10-11) : une compaction dit `working` puis `done`, sans rien qui la distingue d'un tour, et le `done` arrive avant la réponse du mod. Un message reçu pendant la compaction lance son tour sans aucun état entre les deux : un seul `working` couvre la compaction et le tour. Le serveur retient donc le `working` d'un membre qu'il compacte (`Pane.held`), et l'applique depuis l'heure de l'issue quand la compaction a été faite sans autre état vu (`settle_compactions`).
- `CSI 8 ; lignes ; colonnes t` (XTWINOPS 8) n'est jamais relayé au vrai terminal (un xterm redimensionnerait sa fenêtre) ; le serveur ne l'accepte que du panneau de la liste du menu, dans les limites de l'écran. La liste demande la taille de son contenu, jamais une taille tirée de celle de son panneau : sinon serveur et liste se répondent sans fin.
- Thème des programmes (996, 2031, 997) : le moteur ne dit le thème qu'à un programme qui a activé 2031, à l'activation puis une fois par changement, et l'oublie (mode 2031 éteint compris) sur un RIS et sur `state=clear:app=recruit`. Les panneaux de recruit demandent `?2031h` au démarrage et remettent `?2031l` à toute sortie, panique et signaux compris (`leave` de `board/keyboard.rs`, par `libc::write`). Un changement de thème du terminal pendant un attach n'est pas suivi : le thème se relit à l'attach.
- `Panel::generation()` (`mux/cards.rs`) est une empreinte de ce que dessinent les cartes : un champ affiché ajouté à `CardData` sans entrer dans l'empreinte donne une carte figée.
- `server.log` est écrit par le serveur (descripteurs 1 et 2, `O_APPEND`) et par `_mod tick` (une ligne par série d'entrées illisibles) : en ajout seulement.
- Instructions de compaction automatique (`AUTO_COMPACT_INSTRUCTIONS`, en anglais, lues par le modèle) : dire que le membre est au repos et attend son prochain message ; jamais « le travail continue juste après », sinon le résumé pousse le membre à reprendre de lui-même un travail fini (vérifié sur un résumé réel le 2026-10-11).

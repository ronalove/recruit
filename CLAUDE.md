# recruit

CLI en Rust qui lance une équipe d'agents Claude Code dans tmux, à partir d'un fichier TOML. Distribué en binaires précompilés, joints aux releases GitHub de ronalove/recruit, par le tap Homebrew ronalove/tap ; Gitea (git.ronan.love) en est un miroir, qui tire GitHub : on ne pousse que sur GitHub (`origin`). Site (page d'accueil et documentation, EN et FR) : https://ronalove.github.io/recruit/, sources dans `site/`.

## Commandes

```sh
cargo build                          # binaire : target/debug/recruit (clippy ne le reconstruit pas)
cargo test                           # tests unitaires, sans tmux ni Claude
cargo fmt && cargo clippy --all-targets -- -D warnings
RECRUIT_LANG=en cargo test && RECRUIT_LANG=fr cargo test   # comme la CI
cd site && bun install && bun run build                    # le site ; un lien interne cassé fait échouer le build
scripts/screenshots.sh [--lang en|fr] [--only team|cli|anim]   # captures du site, avec de vraies sessions Claude
```

Avant de rendre un travail : `cargo fmt`, clippy sans avertissement, `cargo test` dans les deux langues. La CI (`.github/workflows/ci.yml`, GitHub Actions) les lance sous Linux et macOS à chaque push et pull request, et construit les binaires musl ; `pages.yml` publie le site quand `site/` change. Plus de Woodpecker pour recruit (désactivé le 2026-10-08).

## Publier une version

`scripts/release.sh X.Y.Z [notes.md]`, sur un Mac, depuis `main` propre et à jour : version dans Cargo.toml, vérifications, binaires macOS (chaîne d'Apple) et Linux musl statiques (cargo-zigbuild : `brew install zig cargo-zigbuild`), commit et étiquette `vX.Y.Z`, release GitHub par `gh` (connecté au compte ronalove) avec les archives et `SHA256SUMS`, puis formule régénérée et poussée dans le tap ronalove/homebrew-tap (son clone `../homebrew-tap`, ou `TAP_DIR`). `--dry-run` construit seulement, dans `target/dist/`. La formule ne s'édite pas à la main : son modèle est dans le script.

## Organisation

- `src/main.rs` : point d'entrée ; `cli.rs` : ligne de commande (clap), aide traduite dans `localize` ; `app.rs` : ce que fait chaque commande, et les trois scénarios d'un `recruit` sans argument.
- `config.rs` : fichiers d'équipe (`.recruit/settings.toml` fusionné avec `settings.local.toml`, `~/.config/recruit/<équipe>.toml`), validation, écriture qui garde les commentaires ; `config/edit.rs` : les modifications du menu (`config::edit`, une écriture groupée et validée), dans le fichier qui donne la valeur.
- `templates.rs` + `templates/` : équipes intégrées. `catalog.toml` donne les rôles de chaque type et de chaque taille ; `fr.toml` et `en.toml` en donnent les textes.
- `wizard.rs` : création interactive ; `ui.rs` : invites (texte et oui/non par inquire) ; `ui/list.rs` : listes de choix dessinées par recruit (crossterm), sans curseur ; `generate.rs` : équipe composée par `claude -p --json-schema`.
- `launch.rs` : lancement d'une équipe ; `tmux.rs` : serveur tmux propre (`-L recruit`) et sa config, création des onglets et grilles (trait `Backend`), colonne des panneaux et bascule du journal ; `layout.rs` : répartition en onglets ; `prompt.rs` : prompt système de chaque membre ; `claude.rs` : exécutable, `claude agents --json`, transcriptions, reprise des conversations, approbation du dossier.
- `bridge.rs` + `mod/` : le mod de recruit (plugin de hooks en TypeScript, embarqué, écrit dans `~/.cache/recruit/mod/<version>/`, passé par `--plugin-dir` si Claude Code ≥ 2.1.287). Le mod est une passerelle sans logique : il appelle `recruit _mod start|tick|submit|command <dossier> <membre>`, JSON en entrée et en sortie, et `bridge.rs` fait le travail (rapports pour le tableau de bord, `/equipe`, `/recruit`, modèle et effort configurés, note de l'équipe à jour).
- `live.rs` : une équipe lancée qui suit ses fichiers après une modification (ajout, retrait, renommage, relances, panneaux déplacés entre onglets sans être arrêtés), et l'ouverture du menu ; `menu.rs` + `menu/` : le menu principal (`recruit _menu <dossier> [--client <nom>] [--nerd]`, dans une fenêtre tmux) ; `menu/sheet.rs` : son état et ce que fait chaque touche ou clic, sans terminal ni fichiers (ce qui touche l'équipe revient en `Effect`, que `menu.rs` exécute) ; `menu/draw.rs` : le dessin et les zones de clic. Des fichiers d'équipe illisibles l'ouvrent en lecture seule (membres tels que lancés, détacher, arrêter). `recruit _edit` (caché) applique des modifications sans menu, pour les tests.
- `canvas.rs` : un écran entier dessiné case par case (`Canvas`, largeurs en colonnes par unicode-width), envoyé par différence avec l'image d'avant (`Painter`), et le terminal rendu tel qu'il était à chaque sortie, panique comprise (`Session`, `PanicGuard`, que `ui/list.rs` utilise aussi) ; `look.rs` : ce que partagent le tableau de bord et le menu (états et leurs icônes, Nerd Font ou Unicode, couleurs des membres et de l'effort, indicateur animé, durées).
- `member.rs` : ce qui tourne dans le panneau d'un membre (`recruit _member [--resume] <dossier> <membre>`) : son Claude, relancé sur la même session quand il s'arrête de lui-même ; la session courante est relevée dans `claude agents` et notée dans `sessions/<membre>` du dossier de l'équipe.
- `board.rs` : panneaux d'une équipe lancée (`recruit _panel dashboard|journal|toggle <dossier>`, sous-commande cachée) ; il écrit aussi, pour le menu, `states.json` (l'état de chaque membre et depuis quand, `at` en secondes) ; `state.rs` : l'équipe telle que lancée, dans `~/.cache/recruit/teams/<session>/team.json`, que lisent les panneaux.
- `i18n.rs` : langue (FR, EN) et macro `t!("français", "english", args…)`. Tout texte vu par l'utilisateur passe par `t!`, dans les deux langues.
- `site/` : Astro Starlight, construit par bun. La documentation dans `src/content/docs/` (anglais) et `src/content/docs/fr/` (mêmes noms de fichiers), la page d'accueil à part, sans l'habillage de Starlight, les captures dans `src/assets/screenshots/`.
- `scripts/screenshots.sh` + `scripts/demo/` : les captures et l'animation du site et des README, faites avec une équipe de démo (« shorty ») dans un serveur tmux de test (`-L rtest-shots`), de vraies sessions Claude, vhs et ffmpeg ; `RECRUIT_NO_USAGE=1` (caché) y masque la ligne d'usage du tableau de bord.

## Décisions (validées par l'utilisateur, octobre 2026)

- v1 : tmux seulement (pas de pilotage direct de Ghostty ni d'iTerm2) ; Claude Code seulement ; FR et EN.
- Une équipe globale n'a pas de dossier : elle travaille dans le dossier où on la lance. Locale et globale ne diffèrent que par l'endroit d'où on peut la lancer.
- `recruit` sans argument : équipe locale → lancée tout de suite ; sinon équipes globales → proposées, jamais lancées sans demander ; sinon → création interactive. `recruit <nom>` : la locale prime sur la globale ; inconnue → création.
- Mode guidé : modèles intégrés (type × taille), plus l'option « Claude compose l'équipe ». Claude compose par métier, comme les rôles intégrés (2026-10-07) : noms de métier (un rôle intégré, sinon métier-spécialité comme `dev-rust`), jamais deux zones collées, accents compris en français.
- Interlocuteurs et agents de travail (décision du 2026-10-06) : `contact = true` marque les membres à qui parle l'utilisateur (à défaut, le premier membre).
  - Disposition : un premier onglet « Interlocuteurs », puis les agents de travail par `tab`, ou dans « Agents ». Chaque groupe fait 6 au plus, réparti à parts égales en « Agents (1) », « Agents (2) »…, y compris pour une petite équipe.
  - Tous les agents gardent un panneau visible, jamais `--bg`.
  - Le prompt dit à un agent de travail de passer par les interlocuteurs plutôt que d'attendre dans son terminal.
- Tableau de bord (décision du 2026-10-07) : deux interlocuteurs au plus, empilés à gauche du premier onglet ; à droite, le tableau de bord au-dessus du journal, lancés par recruit lui-même et nourris de `claude agents --json` et des transcriptions. `Alt+j` fait passer le journal de complet à réduit (ses trois derniers messages), puis masqué, puis complet (2026-10-07) ; il est réduit au lancement. `dashboard = false` s'en passe (interlocuteurs côte à côte).
- Panneaux, direction B choisie sur maquettes (2026-10-07) : une carte par membre (nom, temps dans l'état, courbe d'activité sur 30 min, contexte), cadre à la couleur de l'état (jaune au travail, vert au repos, rouge en attente), sans modèle, effort ni dernier outil. Disposition : voir plus bas. Journal : deux lignes par message. Maquettes : https://claude.ai/artifact/CztErLpVy96TGm4doc9kZS
  - Retouches (2026-10-07) : indicateur animé à gauche du nom au travail, icône de l'état sinon. En haut : l'heure, le nombre de membres par état en icônes et les raccourcis ; plus de légende, et plus le nom de l'équipe, déjà dans la barre tmux. En bas : l'usage 5 h / 7 j sur une ligne. Icônes Nerd Font quand le terminal les embarque (Ghostty, kitty, WezTerm), Unicode d'une colonne sinon ; pas de dépendance à une police.
  - Cartes sur deux lignes, variante « Trait » (2026-10-07, maquette https://claude.ai/artifact/QsLCTZPnNqgkg1ij8T3VMf ; remplace le cadre et les couleurs ci-dessus) : à gauche, un trait « capsule » à la couleur de l'état, sur toutes les lignes de la carte (╻ en haut, ┃ au milieu, ╹ en bas : il commence et finit au milieu de la première et de la dernière ligne, et deux cartes ne se touchent pas), une ligne vide entre les cartes, courbe inchangée. L'état se lit par l'intensité : au travail jaune vif et nom en gras, en attente rouge vif, au repos gris et nom atténué. Dans le titre, à gauche du temps, le modèle (Haiku, Sonnet, Opus, Fable) et l'effort aux couleurs de Claude Code, selon la place : « Opus █ xhigh » (signe de niveau et mot ; low jaune, medium vert, high et xhigh violet, max arc-en-ciel), sinon « Opus █ », sinon « Opus », sinon rien, la même forme pour toutes les cartes de même largeur ; le modèle, l'effort et le temps alignés en colonnes d'une carte à l'autre de même largeur, le temps écrit court (12s, 22m, 1h05) ; le modèle toujours atténué ; l'effort toujours vif. Une ligne « ce qu'il fait », selon la forme de la carte, sur deux lignes au plus quand le texte dépasse et qu'il y a la place (coupé aux mots ; « … » seulement faute de place) : un résumé de la demande en cours par Haiku (`$.model.complete` dans le mod, préparé par `bridge.rs`), une fois par nouvelle tâche ; les modèles actuels n'ont plus de liste de tâches ; au repos, la dernière tâche, atténuée, sous sa forme finie (« ✓ Version 0.6.2 publiée »), que Haiku donne dans le même appel. Le contexte passe en orange dès 80 % du seuil de compactage automatique du modèle, en rouge à l'avertissement de Claude Code (20 000 jetons avant) ; un clic sur celui d'un membre au repos propose de compacter, après confirmation.
  - Clic (2026-10-07) : un clic sur la carte d'un membre, ou sur l'expéditeur ou le destinataire d'un message du journal, mène à son panneau.
  - Disposition (2026-10-07) : les interlocuteurs, puis les agents en attente, ceux au travail, puis ceux au repos du plus récent au plus ancien. Chaque carte a sa forme : pleine largeur avec ce qu'il fait sur deux lignes ou une, côte à côte avec une ligne ou aucune, ou, pour un agent au repos, son nom dans la liste. Dans cet ordre, chaque carte prend la plus riche qui laisse la place à toutes les suivantes dans leur forme la plus sobre. Les actifs restent en pleine largeur sans texte coupé tant que possible : la liste des noms au repos se réduit à une ligne (« … et N autres ») avant qu'un actif perde du texte. Une carte sans tâche commence côte à côte et ne s'élargit qu'avec la place qui reste. En dernier recours, « … et N de plus ». La disposition ne change qu'avec les cartes, leurs états ou le panneau.
- Barres de Claude Code (décision du 2026-10-07) : sauf l'interlocuteur principal (le premier interlocuteur), les membres n'ont ni la ligne d'état de l'utilisateur (`--settings` au lancement, pour la session seulement, et seulement si ses réglages en définissent une ; en plein écran, sa ligne reste, vide) ni l'aide du bas (le mod masque `PromptHint` et `SessionMode`). La saisie et la ligne du mode de permission restent : en 2.1.292, rien ne peut les masquer, ni les lier au focus.
- Stabilité et sortie (décision du 2026-10-07) : un membre arrêté (`/exit`, plantage) est relancé après 2 s sur sa session (Ctrl-C : un shell à la place ; pas de relance après deux départs ratés ni à l'arrêt de l'équipe). Revenir sur une équipe qui tourne relance les membres arrêtés, rouvre le tableau de bord, propose de reconstruire si des panneaux manquent. `Alt+q` et le bouton « quitter » de la barre ouvrent un menu : détacher ou arrêter l'équipe.
- Mod passerelle (décision du 2026-10-07) : toute la logique reste en Rust. Il ajoute au tableau de bord le modèle, l'effort, le contexte et l'usage 5 h / 7 j, sert `/equipe` (`/team`) et `/recruit` (voir « Menu principal »), et donne à chaque membre la composition à jour de l'équipe.
- Menu principal (décision du 2026-10-07) : `/recruit` (même nom en FR et EN) remplace `/regler`. Il ouvre une fenêtre tmux (`display-popup` qui lance `recruit _menu`). `Alt+r` l'ouvre aussi, ainsi qu'un bouton « menu » dans la barre, à gauche de « quitter » ; `Alt+q` reste.
  - Entrées : pour chaque agent, modèle, effort, nom, rôle et instructions, interlocuteur, onglet, mode de permission, relancer (en reprenant sa conversation ou à neuf), retirer ; nouvel agent (rôle intégré, composé par Claude, ou saisi) ; pour l'équipe, tableau de bord oui ou non, tout recharger à zéro (contextes vidés pour tous), détacher, arrêter.
  - Les modifications sont permanentes et prennent effet tout de suite sur l'équipe lancée. Elles s'écrivent dans le fichier qui donne aujourd'hui la valeur (`settings.local.toml` s'il a la clé, sinon `settings.toml` s'il l'a, sinon le fichier qui définit le membre ou l'équipe, `settings.toml` d'abord), jamais dans `~/.claude/settings.json` ni ailleurs. Si la valeur choisie est celle que donnent les couches en dessous (`settings.toml` sous le local, puis l'équipe, puis le défaut), la clé est retirée de ce fichier, et une table devenue vide avec elle ; le menu affiche ce que donne « défaut » et d'où ça vient. Renommer et retirer touchent chaque fichier qui définit le membre ; un nouveau membre va dans le fichier qui définit l'équipe.
  - À chaud : le modèle et l'effort passent par les requêtes du membre ; le rôle, les instructions et la composition de l'équipe par une note jointe à son prochain message, sans déclencher de tour. Un membre est relancé sur sa conversation s'il est renommé, si son mode de permission change, ou si son modèle ou son effort ne peut pas passer par les requêtes ; le menu le confirme s'il est au travail.
  - Garde-fous : retirer le dernier membre est refusé ; retirer ou passer en agent le seul interlocuteur demande qui le remplace ; deux noms qui ne diffèrent que par la casse, ou un nom porté par une session ouverte dans le dossier, sont refusés.
  - Écran, direction A « Fiches » choisie sur maquettes (2026-10-08, https://claude.ai/artifact/21QAPjfCZf8wBrbpzvGysV ; remplace la suite de listes) : à gauche les membres comme au tableau de bord (trait et icône de l'état, nom, temps, modèle atténué et effort en couleur), interlocuteurs puis agents, « + Nouvel agent » en dessous ; à droite la fiche du membre choisi, un champ par ligne, l'origine de la valeur à droite, atténuée, et sous la fiche une ligne qui dit ce que donne « défaut » et quand le changement prend effet. ←→ changent une valeur sur place, ⏎ déroule la liste des valeurs (« défaut : … » en tête, la valeur actuelle marquée) ou édite un texte en place (nom, rôle ; les instructions dans l'éditeur), les garde-fous répondent pendant la frappe ; les confirmations s'ouvrent au centre, sur « Annuler », le reste atténué. ←→ n'appliquent tout de suite qu'un modèle ou un effort qui passe par les requêtes ; sinon la valeur est préparée (« à valider ») et ⏎ l'applique. En bas, le résultat du dernier changement, puis les actions d'équipe en boutons avec leur touche. Tout se clique. En fenêtre étroite, la liste se réduit aux noms et l'origine passe sous la fiche. Palette `/` de recherche d'actions dans un second temps.
  - Critère technique : la performance (choix de l'utilisateur, 2026-10-08) : premier écran sans attendre, aucune entrée-sortie lente sur le chemin du dessin, redessin par différence. Dessiné en crossterm à la main, comme le tableau de bord et `ui/list.rs`, sans ratatui.
- Doublons de noms (décision du 2026-10-07) : on n'arrête ni ne renomme rien. Le prompt donne à chaque membre la session tmux de son équipe : si ListAgents montre plusieurs sessions sous un même nom, il écrit à celle dont la ligne indique « tmux <session>:… », à l'adresse « nom [ref] ». Plus d'avertissement au lancement ; le tableau de bord nomme les doublons au-dessus de l'usage, s'il reste de la place. Une session au nom d'un membre déjà ouverte dans le dossier de l'équipe est toujours refusée au lancement.
- Sous macOS, les raccourcis s'affichent avec ⌥ (⌥j, ⌥q, ⌥r) ; ailleurs Alt+j (décision du 2026-10-07).
- Sous macOS, la langue du système prime sur `LANG` (Ghostty impose `en_US.UTF-8`).
- Libellés courts (décision du 2026-10-08) : le menu Alt+q propose « Détacher » (d), « Quitter » (q, arrête l'équipe), « Annuler » (a) ; en anglais Detach (d), Quit (q), Cancel (c) ; sans explication dans le libellé. Le menu /recruit suit : « Quitter » (q) remplace « Arrêter », et « Réinitialiser » (« Reset ») remplace « Relancer tout à neuf ».
- Sous-agents au tableau de bord (décision du 2026-10-08, option A) : sous la carte d'un membre, une ligne par sous-agent (type, description, temps court), un sablier en tête (Nerd Font, sinon ⧗), l'état lu par l'intensité (au travail jaune vif, fini atténué, échec ou arrêt en rouge), à plat même pour un sous-agent de sous-agent. La ligne apparaît au lancement ; à la fin elle passe en ✓ atténué une dizaine de secondes puis disparaît, un échec reste rouge un moment. Données : `$.agent.list()` du mod, passé par le tick (2 s) à `bridge.rs` ; le tri et les durées en Rust. Dans la disposition, c'est un degré de richesse de plus de la carte (liste, sinon « N sous-agents », sinon rien), jamais au détriment du « ce qu'il fait » d'un actif. L'interlocuteur principal garde aussi les pastilles de Claude Code. Le menu ne les montre jamais, ni les teammates : temporaires ou propres à Claude Code, ils n'ont rien à y régler. Les teammates (équipes d'agents de Claude Code lancées par un membre, reconnus à `teammateId`) s'affichent à part : leur nom, une icône de personne, au travail ou en attente, sans disparition après un tour ; la ligne part quand ils quittent `$.agent.list()`, et un état figé trop longtemps passe en inconnu, puis disparaît (contre les fantômes d'un panneau mort).

Chaque fichier source (Rust, TypeScript du mod, scripts, code du site) commence par `SPDX-License-Identifier: AGPL-3.0-or-later` et `Copyright (C) 2026 Ronan Lamour`, dans la syntaxe de commentaire du fichier ; un nouveau fichier aussi.
- Noms écrits à la main (décision du 2026-10-08) : à chaque lecture des fichiers, les noms d'équipe et de membre suivent les règles de la création (assistant, `new`, menu), casse comprise ; sinon l'équipe ne se lance pas, et le message nomme le fichier, le nom et la raison. `recruit edit` ouvre quand même le fichier.

## Pièges

- Les cibles tmux de session s'écrivent `=nom` (correspondance exacte), et `=nom:` pour `set-option` (qui attend une cible de panneau).
- Les panneaux lancent `/bin/sh -c '<claude …>; exec "$SHELL" -l'` : le shell qui reste après Claude doit être celui de l'utilisateur, et le script doit être POSIX (le shell par défaut peut être fish).
- Un `--dry-run` ne finit pas sur un shell de connexion : son message d'accueil recouvrirait le texte du panneau.
- `Alt+j` est lié à chaque lancement (le chemin de recruit peut changer), pour tout le serveur : la commande lit `#{@recruit_state}`, l'option de la session où on appuie. `send-keys` ne déclenche pas les raccourcis : pour tester, `run-shell -t <panneau>` avec la commande liée.
- Le clic dans les panneaux : `#{mouse_line}` (le texte des messages, écrit par les agents) ne passe que par `set-option -p -F` dans une option du panneau, relue ensuite par `recruit _click` ; jamais dans le texte d'une commande ni de `run-shell`. tmux ne redéveloppe pas une option relue (vérifié en 3.7c).
- Le mod : `/model` et `/effort` lancés par `$.command.run` enregistrent le choix comme défaut de l'utilisateur dans `~/.claude/settings.json`. Le modèle et l'effort changés depuis le menu passent donc par `turn.step` (`next({ ...e, model, effort })`), là seulement où `MemberInfo.model`/`effort` diffèrent de `--model`/`--effort` de `MemberInfo.argv`. `turn.step` veut un identifiant complet (`sonnet` y échoue) : `bridge.rs` traduit les alias (table `ALIASES`, à tenir à jour). Le retour au défaut de Claude Code, ou un modèle sans identifiant connu (`opus[1m]`), ne passe pas par la requête : `bridge::applies_live` le dit, et le membre est relancé avec reprise. Le mode de permission ne change pas à chaud (`setMode` n'existe que dans la réponse à une demande de permission) : relance avec reprise. En testant avec de vraies sessions, vérifier que `<profil>/settings.json` (`~/.claude`, ou `$CLAUDE_CONFIG_DIR`) ne change pas.
- Le prompt de `--append-system-prompt-file` n'est ni une section de `prompt.section` ni de `prompt.compose` (2.1.293) : il s'ajoute après, et une conversation reprise par `-r` le garde tel qu'au départ. Le prompt à jour passe donc par une note jointe au message entrant (`prompt.submit`, `context`), que l'utilisateur ne voit pas : `_mod submit` ne la donne que si le prompt a changé depuis ce que la conversation a reçu (`prompted/<session>.json` du dossier d'état), et de nouveau après une compaction ; en échec, ou au-delà de 3 s, le message passe sans note. Le `--append-system-prompt-file` de `MemberInfo.argv` nomme le prompt d'une conversation neuve, même pour un membre repris : une conversation reprise se reconnaît à son fichier, déjà là au démarrage (une neuve ne l'a qu'à son premier message). Les prompts sont écrits un fichier par contenu, jamais réécrits en place.
- Le mod se vérifie avec `claude plugin validate mod` (fait par `release.sh`), ses types avec `bunx -p typescript tsc -p mod` : Claude Code écrit ceux de sa version dans `mod/.claude-plugin/types/` (ignorés par git) dès qu'il charge `--plugin-dir mod` ; le fichier installé avec le marketplace peut dater d'une version antérieure. Le validateur exige `$` passé seulement à des fonctions de premier niveau, et `$.env.get` avec un nom littéral.
- Les commandes que le mod enregistre (`$.command.register`) ne prennent pas l'espace de noms du plugin : `/recruit` marche bien que le plugin s'appelle recruit ; Claude Code préfixe seulement leur sortie par « recruit: ».
- tmux 3.5 au minimum (`MIN_VERSION`) : `display-menu -M` en a besoin. `display-popup` ne développe aucun format dans sa commande (seulement `-d`, vérifié en 3.7c), et depuis 3.5 la lance par `default-shell` (fish possible) : `Alt+r` et le bouton passent par `run-shell -b "recruit … _menu '#{@recruit_state}' --client '#{client_name}' --popup"`, qui ouvre la fenêtre avec des valeurs concrètes et une commande simple.
- Reprendre la session d'un membre : pas la plus récente qui porte son nom (une session qui n'a rien échangé n'a pas encore de titre, et une plus ancienne serait reprise), mais celle que `member.rs` a relevée pendant qu'elle tournait.
- Tester un raccourci ou le menu tmux : il faut un client. `script -q /dev/null tmux -L rtest-<nom> attach -t =<équipe> &`, puis `send-keys -K -c <client> M-q`. Un `display-menu` lancé depuis la ligne de commande attend qu'on ferme le menu.
- Les menus tmux : un menu ne se voit pas dans `capture-pane`. Un `display-menu` lancé hors d'une liaison souris (depuis `recruit _click`, par exemple) ne gère la souris qu'avec `-M`, et `-M` seul le ferme au premier mouvement hors du menu : il faut `-M -O`. tmux refuse sans rien dire un second menu sur un client qui en a déjà un.
- Pour tester les écrans interactifs sans terminal : les piloter dans un serveur tmux de test, un par membre (`tmux -L rtest-<nom>`, `send-keys`, `capture-pane`), avec `XDG_CONFIG_HOME` et `XDG_CACHE_HOME` dans un dossier temporaire. Ne jamais arrêter le serveur d'un autre.
- Le mod remplace `PromptHint` par trois blancs en `marginLeft: -3` (`noHint`), dessinés sur le « · » que Claude Code laisse après le libellé du mode. C'est fragile : si Claude Code change ce séparateur, ou met l'aide avant le mode, le « · » revient sans bruit. Quand le libellé passe à la ligne (panneau très étroit : 26 colonnes en mode bypass), le « · » reste, comme sans `noHint` (vérifié en 2.1.293).
- En plein écran, Claude Code garde une ligne pour toute `statusLine`, même une qui n'affiche rien, et `--settings` ne peut pas l'enlever (2.1.293). QUIET ne fait donc que remplacer celle des réglages, et ne se passe que s'il y en a une (`claude::status_line`) : sinon, il ajouterait sa propre ligne.
- Les réglages que lit Claude Code (2.1.293) : `<profil>/settings.json` ; `<cwd>/.claude/settings.json`, jamais à la racine git ; `<racine git>/.claude/settings.local.json`, plus l'ancien `<cwd>/.claude/settings.local.json`. La racine d'un worktree est son dépôt principal (Claude Code suit `.git`, `gitdir` et `commondir`), sauf pour un dépôt nu. Les réglages gérés priment sur `--settings`.
- ListAgents montre la session tmux de chaque session (`tmux <session>:@<fenêtre>.%<panneau>`), pas le socket : deux équipes du même nom sur deux serveurs tmux donnent la même ligne.
- Les listes de choix (`ui/list.rs`) se redessinent en place : elles remontent d'autant de lignes qu'elles en occupaient (largeurs en colonnes, `unicode-width`). Quand le terminal rétrécit, tmux replie les lignes trop longues et garde ce repli sur les lignes réécrites ensuite ; élargi, il les recolle, la liste tient moins de lignes que prévu et le redessin efface ce qui est au-dessus. Chaque redessin efface donc sa première ligne entière (`Clear(CurrentLine)`), l'écrit, puis efface jusqu'en bas (`Clear(FromCursorDown)`) : effacé jusqu'en bas depuis le coin en haut à gauche, l'écran entier passerait dans l'historique de tmux (`scroll-on-clear`) à chaque touche (vérifié en 3.7c). La place sous la liste vient de `cursor::position()`, qui interroge le terminal par stdout : seulement si stdout est le terminal.
- Le menu ne fait rien de lent avant sa première image : `live::popup` pose une seule question à tmux (`display-message -p -c <client>` : taille et terminal du client), d'où la taille de la fenêtre (`tmux::popup_size`) et `--nerd` ; les états viennent de `states.json` s'il date de moins de 3 s (`at`), sinon de `claude agents --json` toutes les 2 s, dans un fil à part ; un état qui ne se voit pas compte comme peut-être au travail. tmux refuse sans rien afficher une fenêtre plus grande que le client (« width too large », vérifié en 3.7c) : `popup_size` ne doit jamais le dépasser (taille inconnue : 80 %).
- tmux garde les mises à jour synchronisées d'un programme dans un panneau, pas dans une fenêtre `display-popup` (3.5a, 3.7c) : chaque image du menu part en une seule écriture, et seulement ce qui a changé (`canvas::Painter`).
- `canvas` écarte les caractères sans largeur (accent seul, ZWJ, sélecteur de variante) : chaque case montre ce qu'elle contient, et une séquence d'emoji s'affiche en morceaux.
- Les fichiers que lisent d'autres processus (`states.json`, `zones.json`, rapports et notes du mod) s'écrivent par `config::write_atomic`, la seule écriture atomique : un `.<nom>.<pid>.tmp` à côté, puis renommé. Une lecture de dossier doit écarter ces fichiers (`prompted/` ne garde que les `.json`).
- La langue est fixée une fois par processus (un `OnceLock`), donc pour tous les tests à la fois : un test qui compare un texte le construit par `t!` (ou `tmux::ALT` pour ⌥/Alt+), jamais en dur. La CI tourne sans locale (anglais) : `RECRUIT_LANG=en cargo test` le reproduit.
- Sous Linux, l'heure d'un fichier vient d'une horloge grossière (un tick) et peut précéder un `SystemTime::now()` pris juste avant l'écriture : ne jamais comparer l'heure d'un fichier à l'heure courante pour savoir s'il est neuf ; écrire un jeton et comparer le contenu (`menu.opened`).
- Captures : Claude Code affiche le forfait du compte (« Claude Max ») dans son accueil, sans réglage pour le masquer (2.1.294) ; `scripts/screenshots.sh` relit chaque panneau avant de capturer et recommence tant qu'un forfait, `/Users/` ou `$HOME` s'y voit. `vhs -q` (0.12.1) quitte avant d'écrire une capture qui termine la tape : une pause en fin de tape.
